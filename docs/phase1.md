## 3. Architecture (PROPOSED)

```
Editor → Storyblok (SaaS, EU region) --publish webhook--> build (Astro, CI) → static files → static host / CDN → visitors
                                                                             + redirect rules (_redirects)
Third-party, client-side: Google reviews widget, form/appointment embed, GA4 / Google Ads tags, cookie consent
DNS (registrar) → points the domain to the static host
```

- No own server, no database (matches the DECIDED static architecture). Storyblok, build and hosting are separate services;
  "same server" does not apply.
- **Storyblok**: organisation owned by the **customer**, we are collaborators. EU region. Space with components mirroring
  `src/content.config.ts`. Visual editor uses the preview deployment with a draft token. Publish → webhook → rebuild.
- **Content flow (DECIDED 2026-10-22)**: the importer writes structured content as **JSON into the repo** (`src/content/`,
  same model as the prototype). This works without a Storyblok account, keeps `verify-content` working and makes every
  import result reviewable. A separate **push script** uploads the JSON to Storyblok via the Management API — a mechanical
  step, not a second migration. After the push, Storyblok is the source of truth and the build reads from it.
- **This repo becomes the production website repo.** Nothing is uploaded by hand: the host builds from the repo (Git
  integration) or CI builds and deploys `dist/`; Storyblok publish triggers the same build. Before that: remove
  `src/variants/` + `variant_*` routes, decide what happens to `reference/` and internal `docs/` (see P9).
- **Hosting**: static host with preview deployments, build hooks and redirects (e.g. Netlify, Cloudflare Pages, Vercel).
  The test phase runs on the same provider as production, so go-live is only a domain switch. Choice: OPEN.
- **Images**: Storyblok is the only media library (migrated + new images). Old `/wp-content/uploads/…` URLs keep working
  via 301 redirects generated by the importer (PROPOSED, see P4). During development images stay hotlinked from the live site.

- Working assumption: the last column (project lead handles the non-dev work, customer does the manual QA).

  checks, DNS and training do not shrink. Overall effect ≈ 40 %.
- Biggest unknowns: number of distinct layouts, existing WP redirects, attachment-page decision, number of review rounds.
- **Recommended first step: pilot** one URL group end to end (e.g. `/lattenroste/`, 21 pages) and track the real hours,
  then recalibrate before fixing the budget.
